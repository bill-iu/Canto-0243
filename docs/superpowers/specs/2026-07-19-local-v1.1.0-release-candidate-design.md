# Local v1.1.0 Release Candidate Design

## Goal

Build and validate the complete `v1.1.0` release candidate locally, then publish
the exact tested artifacts as the formal release without rebuilding them. The
initial release includes the Windows x64 portable zip and production PWA. The
macOS Intel tarball may be added later to the same tag and release.

This replaces the proposed `/beta/` Pages channel. GitHub Pages remains on the
current formal version throughout local acceptance.

## Source and release identity

1. Merge `dev` into `main` through a reviewed pull request before creating any
   release candidate artifact.
2. Build from a clean local `main` that exactly matches `origin/main` and already
   contains `origin/dev`.
3. Reserve `v1.1.0` as the candidate version, but do not create or push its tag
   until the candidate passes maintainer acceptance.
4. Bind every artifact to the full source commit and the same locally built
   lexicon snapshot.
5. Do not publish a GitHub prerelease and do not deploy a `/beta/` PWA.

## Candidate artifacts

One local orchestration entry point produces the complete candidate set:

- `lyrics.db`
- `words-lexicon.json`
- `canto-0243-portable.zip` for Windows x64
- a production-path PWA bundle built for `/Canto-0243/`
- a packaged Pages artifact containing that PWA bundle
- the existing Windows portable fingerprint sidecar
- an RC manifest containing the version, full source commit, build time,
  validation results, file sizes, and SHA-256 for every candidate artifact

The PWA, lexicon exports, and Windows portable must all use the same `lyrics.db`.
The RC manifest is the immutable hand-off between local acceptance and publish.

## Local build flow

The candidate builder must fail unless all of the following are true:

- the current branch is `main`
- the worktree is clean before generated ignored artifacts are created
- local `main` equals `origin/main`
- `origin/dev` is an ancestor of `origin/main`
- `v1.1.0` does not point to another commit
- required build tools and inputs are available

It then performs these operations in order:

1. Build the project lexicon into `lyrics.db` using the repository's existing
   ingest path.
2. Run lexicon, POS, query, metadata, and schema checks.
3. Export `words-lexicon.json` from that database.
4. Build the production PWA for `/Canto-0243/` and package its output without
   changing the files after validation.
5. Build the Windows x64 portable bundle and zip, stamped as `v1.1.0`.
6. Run the formal candidate test suite.
7. Hash all deliverables and write the RC manifest last.

If a source file, database, generated artifact, or requested feature changes
afterward, the entire candidate is invalid and must be rebuilt and reaccepted.

## Acceptance

Development servers are convenience checks, not release evidence:

- `npm run dev` provides fast PWA interaction checks.
- the local portable launcher provides fast host interaction checks.

Formal acceptance uses the actual candidate artifacts:

- serve the built PWA through a preview server and exercise
  `/Canto-0243/`, service-worker registration, offline caching, lexicon load,
  search, and the three-axis POS filters
- extract the Windows zip to a new unrelated path and launch it with only its
  bundled runtime
- verify readiness, search, POS filters, shutdown, version, source commit, and
  database fingerprint
- run the existing unit, smoke, TypeScript, lint, Vite, portable-host, and
  PWA/portable parity gates that apply to the changed feature set
- recompute every RC manifest hash after testing

The maintainer explicitly accepts or rejects that manifest. A rejected candidate
is never published.

## Exact-artifact publishing

Publishing consumes the RC manifest; it does not invoke any compiler, database
builder, exporter, or portable packager.

The publisher must:

1. Reconfirm clean `main`, exact `origin/main`, merged `origin/dev`, and the
   source commit recorded in the manifest.
2. Recompute artifact hashes and reject missing, extra, or changed deliverables.
3. Confirm `v1.1.0` and its GitHub Release do not point to a conflicting source.
4. Create a `v1.1.0` draft release at the accepted commit.
5. Upload the tested database, lexicon JSON, Windows zip, Pages artifact,
   portable fingerprint, RC manifest, and checksums.
6. Verify the remote asset names and sizes before changing public state.
7. Deploy Pages by downloading and unpacking the uploaded Pages artifact. The
   Pages workflow must not run Vite or reconstruct the bundle.
8. Verify the live Pages version, readiness, database fingerprint, and a bounded
   search/POS smoke.
9. Publish the draft as the formal `v1.1.0` release only after Pages succeeds.

The existing tag-push Pages build is replaced by an explicit deploy-existing-
artifact workflow. This removes the race where a new tag can trigger Pages before
the release has finished uploading `lyrics.db`.

## Failure and retry semantics

- Source, hash, branch, test, or artifact mismatch fails closed before publish.
- Upload failure leaves a draft release; it does not alter the current Pages
  deployment.
- Pages deployment uses GitHub Pages' atomic replacement. A failed deployment
  must not unpublish or delete the current site.
- Upload or Pages deployment may be retried from the same accepted artifact set.
- Retry must not rebuild or silently replace an artifact.
- If a rebuild is requested, the old manifest is invalidated and the full local
  acceptance cycle starts again.
- Temporary draft/tag state from a failed first publication must be inspected
  and resolved explicitly; the publisher never force-moves a conflicting formal
  tag automatically.

## Later macOS supplement

The first formal publication is complete with Windows x64 and Pages. A maintainer
may later check out the same `v1.1.0` tag on macOS Intel, download the release's
`lyrics.db`, build the tarball, verify its portable fingerprint, and upload the
tar plus sidecar to the existing release. This supplement does not change the
Windows zip, PWA artifact, database, tag, or release version.

## Repository changes in scope

- add the local RC build/manifest orchestration
- add a publish-existing-candidate path with strict manifest validation
- change Pages deployment to consume the uploaded Pages artifact
- add self-checks for source identity, artifact integrity, and no-build publish
- update release and PWA maintainer documentation

No new runtime dependency, secondary Pages site, prerelease channel, or macOS
cross-build is introduced.

## Completion criteria

- `dev` is merged to `main` through PR before the candidate build
- one accepted manifest binds all `v1.1.0` initial artifacts to one commit and DB
- the Windows zip passes a relocated clean-extract smoke test
- the built PWA passes production-path, offline, database, search, and POS checks
- publish performs zero compilation, export, database build, or packaging steps
- the deployed Pages hashes originate from the accepted uploaded artifact
- `v1.1.0` becomes formal only after live Pages verification
- the release remains able to accept the macOS Intel tarball later
